# OrderX Product Requirements Document

版本：1.0  
日期：2026-06-23  
口径：现状基线 + 下一阶段规划  
适用范围：OrderX 票务/商品抢购运营平台

## 1. 背景

OrderX 是一个面向票务抽选、商品抢购和订单执行的运营后台系统。系统以 RuoYi-Vue-Plus 后端和 Vue 管理端为基础，结合 Python、Go、Chrome 扩展等外部执行器，实现从账号资源准备、活动解析、任务编排、自动执行到结果追踪的完整闭环。

当前系统已经不再是单一自动化脚本，而是一个多组件协同平台：

- Java 后端负责权限、资源管理、任务编排、状态持久化、审计和对外接口。
- Vue 管理端负责平台配置、账号池、邮箱池、任务创建、订单记录和运营查看。
- Python 执行器负责 LivePocket、Jump Shop、Hands Form 等平台的注册、登录、活动解析、抽票和抢购执行。
- Go 执行器用于商品抢购下单执行调度。
- Chrome 扩展用于 Hands Form 页面自动填写、提交和结果回写。
- Redis 用于延迟调度、执行队列、结果流和跨进程协调。

## 2. 产品目标

### 2.1 当前阶段目标

建立一个可运营、可追踪、可扩展的票务和商品抢购任务平台，支持运营人员批量管理账号与邮箱资源，创建抽票或抢购任务，按时间或立即调度执行器执行，并在后台查看任务进度、订单状态、邮件结果和异常原因。

### 2.2 成功标准

- 运营人员可以在后台完成平台、账号、邮箱、号码和任务的日常维护。
- 抽票和抢购任务可以绑定多个账号并生成可追踪执行记录。
- 执行器可以通过 HTTP 或 Redis 与后端协同，回写执行进度和结果。
- 任务执行失败时，后台能够保留失败原因、原始摘要和审计记录。
- 邮件同步可以支撑验证码、激活链接和抽选结果解析。
- 生产发布流程可复用，并支持后端、前端、Python 执行器分别部署和回滚。

## 3. 用户角色

### 3.1 系统管理员

负责系统用户、权限、菜单、基础配置、部署配置和故障排查。

### 3.2 运营人员

负责维护平台、账号池、邮箱池、号码池，创建任务，发起执行，查看结果，并处理异常账号或失败任务。

### 3.3 执行器服务

包括 Python 服务、Go 服务和 Chrome 扩展。它们不是人工用户，但需要作为系统协作者领取任务、获取账号上下文、请求验证码、上报心跳和回写结果。

### 3.4 外部平台

包括 LivePocket、Jump Shop、Hands Form 以及后续可能接入的票务或电商平台。系统通过平台适配器隔离不同平台差异。

## 4. 范围

### 4.1 当前范围

- 平台配置管理。
- 号码池管理。
- 账号池管理。
- 邮箱账号池和邮件记录管理。
- 邮件同步、解析、转发和导出。
- 批量注册和批量登录。
- LivePocket 活动解析、抽票任务、批量抽票任务和抽票结果追踪。
- Jump Shop 商品信息解析、注册、登录和抢购下单执行。
- Hands Form 账号快速创建和 Chrome 扩展执行。
- 任务管理、订单执行记录、支付状态标记和审计日志。
- Redis 队列、延迟调度和执行结果消费。
- 生产发布、验证和回滚流程。

### 4.2 暂不纳入当前范围

- 对外商业化租户计费。
- 完整风控策略平台。
- 自动处理 3DS 支付挑战。
- 所有外部平台页面结构变化的自动适配。
- 面向普通消费者的前台页面。
- 对执行成功率作强 SLA 承诺。

## 5. 业务对象

### 5.1 平台

平台代表一个外部票务或商品站点。平台需要配置编码、名称、适配器类型、环境、启用状态、能力标识和下单接口等信息。平台只允许禁用，不允许删除，以避免破坏历史任务和执行记录。

### 5.2 号码

号码用于需要手机号身份或短信能力的平台。系统维护号码、国家区号、供应商、状态和备注，并记录号码与平台、账号之间的关系。

### 5.3 账号

账号是任务执行的核心资源。账号隶属于平台，可绑定手机号和邮箱，保存账号信息、注册请求上下文、登录请求上下文、账号状态、登录状态、最近错误、验证码和激活链接等数据。

### 5.4 邮箱账号

邮箱账号用于注册、登录、验证码获取、激活链接获取和抽选结果解析。系统支持批量创建、状态变更、同步邮件、查看邮件记录、全局邮件总览、导出和重解析。

### 5.5 活动

活动表示一个待抽票或抢购的外部活动。活动可由后台手动配置，也可由 Python 解析外部链接后生成活动标题、报名时间和场次信息。

### 5.6 任务

任务表示一次运营编排。任务可分为普通抢购和抽票两类，包含平台、任务名称、任务状态、执行时间、预热时间、购买数量、配置快照、绑定账号和备注。

### 5.7 批量抽票任务

批量抽票任务用于同时管理多个抽票活动项和多个场次。它包含来源链接、活动项、场次计划、绑定账号和执行汇总。

### 5.8 订单执行记录

订单执行记录是每个账号执行一次任务的流水。记录包含任务、平台、账号、购买类型、配置快照、当前步骤、步骤状态、支付状态、订单号、执行状态、失败原因、心跳、执行器标识和原始结果。

### 5.9 审计事件

审计事件用于记录关键业务操作，例如批量注册、批量登录、任务调度、账号资料更新、执行失败等。

## 6. 核心业务流程

### 6.1 账号准备流程

1. 运营人员配置或启用目标平台。
2. 运营人员导入号码或创建邮箱账号。
3. 运营人员发起批量注册。
4. Java 后端创建注册批次和明细。
5. Python 执行器执行注册流程。
6. Python 按账号发布结果事件。
7. Java 消费结果并更新账号池、批次状态和明细状态。

### 6.2 登录准备流程

1. 运营人员选择平台和账号，发起批量登录。
2. 系统创建登录批次和明细。
3. Python 执行登录。
4. 如需要邮箱验证码，Python 通过后端接口获取或等待验证码。
5. 后端记录登录请求上下文和登录结果。
6. 登录成功账号进入可执行状态。

### 6.3 LivePocket 抽票流程

1. 运营人员输入 LivePocket 活动链接或 tickets 链接。
2. Java 后端创建活动解析记录并写入 Redis 解析队列。
3. Python 解析活动标题、报名时间和场次信息。
4. Java 消费解析结果并保存历史记录。
5. 运营人员创建抽票任务，选择场次、账号和执行时间。
6. Java 生成账号级执行记录和场次计划。
7. 到达执行时间后，Java 将任务写入 Python 抽票队列。
8. Python 执行抽票并回写状态。
9. 邮件同步解析抽选结果，更新执行记录。

### 6.4 批量抽票流程

1. 运营人员创建批量抽票任务，维护多个活动项和场次。
2. 系统绑定账号并保存任务配置。
3. 运营人员发起立即执行或按计划执行。
4. Java 按活动项、场次、账号生成执行记录。
5. Python 执行器执行具体报名。
6. 后台展示批量任务进度和各活动项结果。

### 6.5 Jump Shop 抢购流程

1. 运营人员选择 Jump Shop 平台并输入商品链接。
2. Python 解析商品标题、商品 ID、变体 ID、库存状态、购买模式和支付模式。
3. 运营人员维护收货和支付资料。
4. 创建抢购任务并绑定账号。
5. 到达预热或执行时间后，Java 将任务写入执行队列。
6. Python 或 Go 执行器完成登录、加购、结算和下单。
7. 执行结果回写订单执行记录。

### 6.6 Hands Form 执行流程

1. 后台生成 Hands Form 待执行任务。
2. Java 将任务写入 Redis 抽票队列。
3. Python Playwright 执行器打开 event.hands.net 页面，填写姓名、假名、邮箱等字段。
4. 页面执行 reCAPTCHA 后提交报名表。
5. 执行器进入确认页后继续提交。
6. 执行器获取登记编号并通过结果流回写后端执行记录。
7. 失败时保存页面 HTML 和截图，供排查页面结构或交互式验证问题。

### 6.7 邮件同步和解析流程

1. 运营人员或系统触发邮箱同步。
2. 后端读取邮箱最新邮件并保存邮件记录。
3. 系统解析验证码、激活链接、抽选结果、申请编号和购买完成状态。
4. 邮件结果更新账号或订单执行记录。
5. 运营人员可在邮件总览中查询、导出、删除或转发邮件。

## 7. 功能需求

### 7.1 平台管理

- 系统应支持平台列表、查询、新增和修改。
- 系统应支持平台启用和禁用。
- 系统应禁止删除平台。
- 系统应支持平台能力标识，包括邮箱、短信、手机号身份、批量注册和批量登录能力。
- 系统应支持根据平台和购买类型返回配置模板。

### 7.2 号码池管理

- 系统应支持号码分页查询。
- 系统应支持批量导入号码。
- 系统应支持按供应商、区号、状态维护号码。
- 系统应支持批量修改号码状态。
- 系统应展示号码已注册平台数和已登录平台数。

### 7.3 账号池管理

- 系统应支持账号分页查询和条件筛选。
- 系统应支持手动新增、修改、删除账号。
- 系统应支持查看可绑定手机号。
- 系统应支持查询可选账号 ID 列表，并标识可用和已占用数量。
- 系统应支持批量注册和批量登录。
- 系统应支持查看注册批次、登录批次和明细。
- 系统应支持提交手工邮箱验证码。
- 系统应支持修改 LivePocket 账号姓氏并记录审计。
- 系统应支持 Hands Form 快速创建账号。

### 7.4 邮箱账号池

- 系统应支持邮箱账号分页查询。
- 系统应支持批量创建邮箱账号。
- 系统应支持批量修改邮箱状态。
- 系统应支持按邮箱同步邮件和批量同步邮件。
- 系统应支持全局邮件同步。
- 系统应支持查看单个邮箱的邮件记录。
- 系统应支持邮件总览列表、导出、删除和重解析。
- 系统应支持邮件转发并记录发送结果。

### 7.5 活动解析

- 系统应支持 LivePocket 活动链接和 tickets 链接解析。
- 系统应支持 Hands Form 活动解析链路。
- 系统应将解析请求写入 Redis 队列异步处理。
- 系统应保存解析状态，包括 queued、running、completed、failed。
- 系统应保留最近解析历史，供任务创建复用。

### 7.6 任务管理

- 系统应支持任务列表、详情、新增、修改、取消和删除。
- 系统应支持普通抢购和抽票两类任务。
- 系统应支持绑定多个账号。
- 系统应支持配置预热时间、执行时间、购买数量和任务选项。
- 系统应支持查看任务过程，包括创建步骤、场次计划、执行汇总和执行记录。
- 系统应支持立即执行和按计划执行。
- 系统应支持失败抽票任务重试。
- 系统应支持 LivePocket 问卷预览，用于确认抽票报名表结构和答案配置。

### 7.7 批量抽票任务

- 系统应支持批量抽票任务列表、详情、新增、修改和状态更新。
- 系统应支持一个批量任务包含多个活动项。
- 系统应支持每个活动项包含多个场次计划。
- 系统应支持绑定多个账号。
- 系统应支持立即执行。
- 系统应展示任务进度、活动项状态和执行汇总。

### 7.8 订单执行记录

- 系统应支持订单执行记录分页查询。
- 系统应支持查看执行详情。
- 系统应记录当前步骤、步骤状态、步骤轨迹、心跳、执行器、尝试次数和原始结果。
- 系统应支持标记支付完成。
- 系统应支持删除执行记录。
- 系统应支持按任务、平台、账号、邮箱、购买类型、订单号、执行状态、支付状态和抽选结果筛选。

### 7.9 执行器接口

- Python 执行器应提供健康检查接口。
- Python 执行器应提供 LivePocket 注册、登录、活动解析、抽票和资料更新能力。
- Python 执行器应提供 Jump Shop 注册、登录和商品解析能力。
- Java 后端应提供外部账号接口，供执行器获取验证码、激活链接、待登录账号和待注册账号。
- Chrome 扩展接口应通过固定请求头密钥鉴权。
- 执行器应能上报任务心跳和最终结果。

### 7.10 审计和监控

- 系统应记录关键业务操作审计。
- 系统应提供 dashboard 汇总，包括平台、任务、执行、账号、邮箱等统计。
- 系统应能通过日志和健康检查定位 Java、前端、Python、Go、Redis 的运行状态。

## 8. 非功能需求

### 8.1 权限

后台操作必须接入 RuoYi 权限体系。列表、查询、新增、修改、删除、执行、导出等操作应使用独立权限编码。

### 8.2 幂等

新增、修改、执行、状态变更、批量同步等写操作应具备防重复提交能力。执行器回写结果时应避免重复事件造成状态错乱。

### 8.3 可追踪

每个任务应能追踪到账号级执行记录。每个执行记录应保留足够信息用于排查，包括任务配置快照、账号、平台、步骤、状态、错误信息和原始摘要。

### 8.4 可恢复

生产发布必须支持备份和回滚。队列任务失败时应能在后台识别失败原因，并支持必要的重试或人工处理。

### 8.5 安全

系统不得将真实密钥、Redis 密码、代理 Token、验证码服务 Key 和线上邮箱密码写入 Git 文档或代码。线上私密配置应通过 `.env.local`、systemd、Docker Compose 或 Secret 渠道维护。

### 8.6 性能

普通后台列表应分页查询。高并发任务写入应优先通过 Redis 队列解耦。活动解析、抽票执行、邮件同步等耗时任务不应阻塞管理端页面请求。

### 8.7 兼容性

前端应遵循 Vue 3 + TypeScript + Naive UI 的现有工程规范。后端应遵循 RuoYi-Vue-Plus 分层结构，使用 Controller、Service、Mapper、BO、VO 的既有模式。

## 10. 验收标准

### 10.1 账号准备

- 可以成功创建邮箱账号并同步最新邮件。
- 可以通过批量注册生成注册批次，并在账号池看到结果。
- 可以通过批量登录生成登录批次，并更新账号登录状态。
- 登录需要邮箱验证码时，系统能提交验证码并继续流程。

### 10.2 抽票任务

- 输入有效活动链接后，系统能生成解析记录并返回解析状态。
- 解析完成后，前端可展示活动标题、报名时间和场次。
- 创建抽票任务后，系统能生成场次计划和账号级执行记录。
- 执行后，执行记录状态能从等待进入执行、成功或失败。
- 失败记录能被筛选，并可发起失败重试。

### 10.3 商品抢购任务

- Jump Shop 商品链接可以解析出关键商品参数。
- 创建抢购任务后，系统能按账号生成执行记录。
- 到达执行时间后，执行器能领取任务并回写执行结果。
- 后台能查看订单号、支付状态和失败原因。

### 10.4 Hands Form 执行

- Chrome 扩展可以通过密钥领取任务。
- 扩展可以上报心跳。
- 扩展成功提交后，后端能保存登记编号。
- 密钥错误或未启用时，接口必须拒绝请求。

### 10.5 邮件处理

- 邮件同步后可在邮箱详情和邮件总览中看到记录。
- 系统能解析验证码、激活链接和抽选结果。
- 邮件总览支持导出和删除。
- 邮件重解析能返回扫描数量、更新数量和失败数量。

## 11. 风险和约束

- 外部平台页面结构、验证码策略、WAF 和风控规则随时可能变化，执行成功率存在不确定性。
- 多执行器架构增加部署和排障复杂度，需要严格保持 Java、Python、Go、Redis 和前端配置一致。
- Redis 队列和数据库状态需要保持一致，否则可能出现任务已取消但队列仍存在的情况。
- 邮件解析依赖邮件格式和收件延迟，抽选结果可能不是实时可得。
- Jump Shop 支付流程遇到 3DS 等强交互场景时，当前策略可能直接失败。
- Hands Form 依赖本地或服务器 Chrome 扩展环境，稳定性受浏览器、页面和扩展权限影响。
